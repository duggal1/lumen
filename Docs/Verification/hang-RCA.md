# Hang RCA — Start and Stop beachball (code-level, before fixes)

**Visual verification NOT DONE — no GUI session in this environment.** Screenshots in this report are absent; findings below are from file evidence plus synthetic watchdog tests. The live `sample <pid>` / Time Profiler pass is listed as NOT DONE in §4.

## §3.1 suspects ruled in or out (with evidence)

| Suspect | Verdict | Evidence |
|---|---|---|
| `finishWriting` / `stopCapture` awaited on main | **Ruled OUT as main-thread block, IN as UI freeze** | `CaptureEngine.stop()` (`Sources/LumenCapture/Capture.swift:260-269`) does `try await stream?.stopCapture()` then `await w.finishWriting()`. It is not `@MainActor`, so it does not block the event loop. It IS awaited by `RecordingSession.stop()` on the session actor while `AppModel.stop()` (`Sources/LumenUI/AppModel.swift:418-431`) keeps the HUD open and `phase = .finishing` until it returns. The beachball here is: HUD visible + main idle but no progress for seconds. The fix is immediate HUD dismiss + background finalization, not a main-thread deadlock. |
| `InputRecorder.stop()` on `@MainActor` | **IN — main-thread hop on stop path** | `InputRecorder.stop()` is `@MainActor` (`Input.swift:152`). `RecordingSession.stop()` does `await input.stop()` from the session actor, hopping to main. Inside, it drains `writeQ` and `axQ` via continuations (suspends, does not block), then writes `cursors.json` + `ax.json` on main. Small but unnecessary main work on the stop path; it also makes stop's latency include main scheduling. Fix: make stop nonisolated. |
| `InputRecorder.start()` on `@MainActor` + cursor poll 30 Hz on main | **IN — start-path main work** | `start()` is `@MainActor` (creates `CGEventTap`, starts a `Thread` with `CFRunLoop`). `RecordingSession.start()` does `await MainActor.run { try input.start() }` (`Session.swift:154`). The tap creation itself is fast, but the 30 Hz `catalog.classify()` loop (`Input.swift:136-142`) hashes `NSCursor.currentSystem` bitmaps on main every 33 ms during the whole recording. That is per-tick main work at audio/meter rate — the SwiftUI update storm suspect. Fix: 10 Hz poll, decimate stats to 15 Hz, HUD never observes raw per-frame state. |
| `SCShareableContent` + device discovery on main | **Ruled OUT (already off main)** | `CaptureEngine.prepare()` (`Capture.swift:174`) runs on the `RecordingSession` actor (cooperative pool), not main. The only main hops are `NSScreen.screens` for `maxFPS` (`Capture.swift:191-193`). That hop is one query, not discovery. `SCShareableContent` itself is still slow (200-500 ms) but does not beachball main. Fix is to run it *during* countdown, not before. |
| `CGEventTap` callback slow work | **Ruled OUT as written, IN as hook risk** | `handle()` (`Input.swift:176-211`) only: reads `e.location`, `shape` lock, `ring.push(ev)`, `liveEventHook(ev)`. No logging, no allocation beyond the `InputEvent` value, no main hop. The risk is `liveEventHook` → `LivePreviewController.hub.event` doing UI work synchronously on the tap thread. That hook is only set when live preview is on, so the default path is clean. Fix: make the hook decimated + non-blocking. Tap-disabled handling (`tapDisabledByTimeout`) already re-enables (`Input.swift:177-179`). |
| Per-frame `@Observable` publishing (meter storm) | **IN — stats at 20 Hz + HUD observation** | `AppModel` poll is `Task { stats = await session.stats(); sleep 50 ms }` (`AppModel.swift:414`) = 20 Hz on `@MainActor`, updating `stats` (`@Observable`) and re-rendering `HUDView` (`HUDView` reads `app.stats?.elapsed`, `micLevel`, `dropped`). The task spec caps UI publishing at 15 Hz. `CAFWriter` level itself is computed on `audioQ`, not main — so the storm is the poll + SwiftUI redraw, not the audio callback. Fix: 66 ms (15 Hz) poll, batch. |
| Analysis at stop on main / high QoS | **Ruled OUT on main, IN as QoS/concurrency** | `RecordingSession.stop()` does no VAD/OCR/transcription. `ProjectSession.analyze()` is only called from the editor after open, via `AnalysisService.run()` which `async let`s 5 analyzers concurrently at default QoS (`Service.swift:80-85`). That violates "max 2, `.utility`, pause while recording". Fix: cap to 2, `.utility`, gate on recording-active. |
| Wrong shutdown order / unfinished secondary writer | **IN — `WebcamRecorder` + `ExtraMic` blocking** | `WebcamRecorder.stop()` calls `session.stopRunning()` synchronously (`Session.swift:69-74`) on the caller (session actor) thread — `AVCaptureSession` stop can block 100 ms+. `ExtraMicrophoneRecorder.stop()` does the same (`ExtraMicrophoneRecorder.swift:78-86`). Both are not main, but they serialize stop. Fix: stop on their own queues / detached, drain before close (already drains via queue hop for ExtraMic). |
| Deadlock SCK queue ↔ writer | **Ruled OUT** | `video()` (`Capture.swift:282-297`) never blocks: `guard vin.isReadyForMoreMediaData else { dropped += 1; return }`. No lock is held across `adaptor.append`. `meta.write` is video-queue-only. No semaphore/group wait on main anywhere in the capture path (`grep` for `semaphore.wait` finds only `Renderer.ensureTargets`, export path). |

## What's next (fixed in the lifecycle pass)

- `RecordingSession` gains an explicit state machine (`idle → preparing → countdown → recording ⇄ paused → stopping → finalizing → ready | failed`) with signpost + `Logger` per transition and per-stage timeout → `failed` with plain-language message. Until this lands, the UI shows `preparing / countdown / recording / finishing` only.
- Start: HUD/countdown within 100 ms, `prepare()` concurrent *during* countdown (currently `prepare` then countdown sequential, so a slow `SCShareableContent` delays the countdown).
- Stop: HUD dismiss within 200 ms, shutdown order stop-capture → drain → endSession → mark finished → `finishWriting` off main → wrap journals → finalize events → publish. "Finishing…" with real progress.
- `hangs.json` for a 10-min soak must be empty — proven by `WatchdogTests` + a live soak when a GUI is available (NOT DONE here).
